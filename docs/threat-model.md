# Threat model

Design notes for the Canton Coin traffic purchase. This is not a penetration test. Fiat on-ramp, card data, and partner geoblocking are out of scope.

## Assets

- **The user's unlocked CC**, spent only by a wallet signature.
- **The validator receiving the traffic** (`PAR::…` on a specific synchronizer).
- **The unsigned transaction** (`prepareExecute` command, disclosed contracts, and `splice/memo`) handed to the wallet to sign.
- **Server secrets**: Scan bearer token, registry bearer token, and Keycloak client secret. These stay in server environment configuration.

## Actors

- **The buyer**, who controls the CIP-0103 wallet and approves the transaction.
- **The operator** of this app and its server-side Scan/registry configuration.
- **Scan and the token-standard registry**, which supply pricing, member traffic lookup, and transfer context.
- **An attacker**: a phisher, a copied or compromised front end, or someone with access to another user's browser session.

## Threats and controls

| Threat | What goes wrong | Control in this app |
| --- | --- | --- |
| App or copied front end asks the wallet to sign something else | A tampered or lookalike front end displays one purchase on screen but sends a different command, recipient, or amount to the wallet. | Signing and submission happen only in the user's CIP-0103 wallet (`prepareExecuteAndWait`). This app has no key and cannot skip the wallet prompt. Whether the signed command matches the screen depends on that wallet showing the unsigned command before the user signs. |
| Validator ID, amount, or memo changed after the user checks it | Traffic burns are irreversible; a mutated target `PAR::…`, byte/CC amount, or `splice/memo` credits the wrong validator or burns the wrong amount. | Review shows the CC amount, byte count, USD/CC rate, and `est.` disclosure. The connected party is the shortened `primaryAccount.partyId` (full id in the tooltip and in the connect dialog). The validator is shown with its party fingerprint removed (full member id in the tooltip, and as the full id on the Validator step). The synchronizer is chosen on the Validator step; the network control appears only when the quote lists more than one domain, and Review does not repeat it. Terms and the jurisdiction checkbox are required. They reset when the amount, amount unit, network, or selected validator changes. Changing the purchase path on Review does not clear them. `/api/purchase/transfer-context` builds `splice/memo` on the server from the posted member id (bare ids are normalized with `PAR::`), the public-registry synchronizer id, and the registry migration id. A posted synchronizer that does not match the registry synchronizer is rejected. Receiver party, CC amount, and input holding cids come from the request body. The wallet approves the prepared command, which is what fixes the recipient and amount. |
| Stale quote burns more CC than shown | CC/USD moves between quoting and signing, causing the user to pay more CC than expected or fail the network minimum. | `lib/purchase/quote-validity.ts` sets the quote end to `opensAt + tickDuration`. Under 60 seconds the state is `warning`. The last 10 seconds (`QUOTE_BLOCK_MS`) are `blocked`. `quoteAllowsSubmission` is false for `blocked`, `expired`, and `invalid`, and when the round contract id is missing. Review calls `assertPurchasePrice` on entry and again on Confirm, each time refetching `/api/quote`. If the CC amount for the same byte count changes, Confirm stays on Review and shows the new amount instead of opening the wallet. Confirm also stays on Review with an error if the refresh fails, the quote is not submittable, or the amount is under the network minimum (`purchaseMinBytes` is at least 200,000 bytes; `coversMinimumPurchaseUsd` / `minimumPurchaseUsd` use the quoted extra-traffic price, which is $12 at $60/MB, with a $0.005 tolerance). A new open-round contract id with the same CC amount does not by itself keep Confirm on Review. Before the wallet opens, `onPurchase` loads purchase context and, when that context's open-round contract id differs from the quote's round contract id, stops with `The CC price changed. Review the updated amount.` and returns to Review without opening the wallet. The Token Standard command contains the exact CC amount the wallet signs. A rejected exercise, including `insufficient-topup-amount`, does not commit, so that attempt does not burn CC. A wallet prompt that is already open can still be signed after the tick; the CC amount inside that command does not change. |
| Locked or unapproved holdings selected as input | A locked Amulet holding, a CIP-0112 allocation, or a holding the user did not intend to spend is consumed. | `listAmuletHoldings` queries Holding V1 and Holding V2 through the wallet's `ledgerApi`, ignores non-Amulet instruments, and drops a Holding-interface row whose lock has not expired. The code does not identify CIP-0112 allocations by name. The legacy path prefers `Splice.Amulet` template rows and does not apply that lock check. It does reject selected input cids that are no longer active (`assertInputAmuletCidsActive`) before building `AmuletRules_BuyMemberTraffic`. No input is spent unless the wallet approves the prepared command. |
| Scan returns a wrong party, participant, or price treated as final | Bad or manipulated Scan output routes traffic to the wrong validator or misstates the price. | `SCAN_BASE_URL` and `TRANSFER_REGISTRY_BASE_URL` are server configuration, not browser inputs. A lookup with more than one validator requires an explicit choice, and each choice shows the full member id. Review shows the shortened party, the fingerprint-stripped validator name, the USD/CC rate, and the `est.` disclosure. It does not show the synchronizer. `fetchPurchaseContext` rejects the purchase when the disclosed `AmuletRules` or open-mining-round contract is on a different synchronizer from the one requested. Transfer context rejects a posted synchronizer that does not match the public registry synchronizer. A transfer-factory disclosed contract keeps the synchronizer id from its payload when one is present; `parseTransferFactoryResponse` does not reject that contract only because the domain differs. |
| Someone connects a wallet session that is not theirs | A shared browser or stale discovery entry connects an unexpected party and tries to spend from it. | Connecting requires an authorized extension or remote wallet session. The header and Review show the shortened party id from `primaryAccount.partyId`. The connect dialog shows the full party id. Confirm stays disabled when the wallet reports `isNetworkConnected === false`. The user can disconnect or switch wallets. Execution still requires the wallet to authenticate and sign. |
| Operator holds a key, signature, CC, or fiat | The operator becomes custodial or exposes user funds/credentials. | Private keys stay in the user's CIP-0103 wallet. The wallet signs and submits through `prepareExecuteAndWait`. On the token-standard path the client sends the receiver from path-status: the reserved `splice_traffic-manager` party, or `TRAFFIC_PURCHASE_RECEIVER_PARTY_ID` when that is set. The legacy path submits `AmuletRules_BuyMemberTraffic`. The transfer-context route does not reject a different receiver party; the wallet prompt is the check on the receiver. This app processes no fiat or card data. The FAQ, Terms, and imprint state this non-custodial model. |
| XSS from Scan error strings | A crafted upstream error string injects HTML/script into the page. | Scan and purchase errors are rendered as React text children. Lookup, quote-refresh, submit, context, and path errors pass through `uiErrorName`. The price-check message (`priceError`) is also a React text child. None of these use `dangerouslySetInnerHTML`. |
| Server secret leaked in client bundle | Scan or registry credentials ship to the browser. | `SCAN_BEARER_TOKEN`, `REGISTRY_BEARER_TOKEN`, and `KEYCLOAK_CLIENT_SECRET` are read in server modules (`lib/scan.ts`, `lib/server/registry-auth.ts`) used by API routes. They are not `NEXT_PUBLIC_` variables and are not imported by client components. |
| Restricted jurisdiction purchase | A user attempts to buy traffic where not permitted. | Review gates wallet confirmation on explicit Terms and `"I may buy traffic in my jurisdiction."` confirmations. This is a self-attestation, not a geoblock. |
| Swapped on-ramp iframe | A malicious iframe replaces a fiat partner widget. | This app has no on-ramp iframe and does not set a Content-Security-Policy `frame-src`. |

## Conclusion

**This app prepares the unsigned transaction; the user's own wallet signs and submits it.** The operator never holds user keys, signatures, CC, or fiat.

## Out of scope

- Penetration testing.
- Fiat on-ramp KYC, card data, partner iframe controls, and partner geoblocking lists.
